# Issue #2 — synthetic retail medallion

Design, data-quality rules, validation approach and operating procedure for the
solution built for [Issue #2](https://github.com/StefanUSI/ms-fabric-agentic-devops/issues/2).

> **No real identifiers appear in this document.** The workspace and folder come
> from `config/environment.local.json`, which is gitignored. This repository is
> public.

---

## 1. Deployment status — read this first

**The solution is authored, tested and planned. It has not been deployed to
Microsoft Fabric.**

Two independent gates are shut:

| Gate | State | Who opens it |
|---|---|---|
| `.agent-manifest.json` → `permissions.mayCallFabric` | `false` | The dispatcher, when Fabric is configured for the run |
| `config/environment.local.json` → `fabric.authorisedForTicket` | `null`, expected `"2"` | A human |

Issue #2 *does* authorise Fabric deployment. But it supplies the target **by
reference** to the local configuration rather than by value — correctly, since
naming a workspace or GUID in a public Issue would be the exposure the ticket
forbids. That local configuration has not been bound to ticket 2.

`CLAUDE.md` rule 5 requires a stop when the local environment configuration is
absent, invalid or ambiguous. Rule 12 forbids weakening a control to complete a
ticket. Setting `authorisedForTicket` would be an agent opening its own gate, so
the agent stopped instead.

**Everything that does not depend on that gate is complete**: item definitions,
orchestration, the deterministic toolbox, 62 offline tests, this documentation
and the reversal plan. What is missing is exactly the set of claims that require
a live run — and those are recorded as *not produced*, never as assumed.

To deploy, a human sets `fabric.authorisedForTicket` to `"2"` and runs:

```powershell
./scripts/fabric/Deploy-Issue2Medallion.ps1 -Mode Plan   # offline, no Fabric call
./scripts/fabric/Deploy-Issue2Medallion.ps1 -Mode Live   # deploys, runs twice, validates
./scripts/fabric/Write-Issue2Evidence.ps1                # sanitizes evidence for commit
```

## 2. Architecture

A four-stage medallion in a single Lakehouse, orchestrated by one pipeline.

```
issue2_00_generate_source   Files/issue2/landing/*.csv        (synthetic source)
        |
issue2_10_bronze_ingest     Tables/issue2_bronze_*            (raw, untyped, unfiltered)
        |
issue2_20_silver_transform  Tables/issue2_silver_*            (typed, validated, deduplicated)
        |                   Tables/issue2_silver_quarantine_sales
        |
issue2_30_gold_build        Tables/issue2_gold_*              (three analytical grains)
        |
issue2_90_validate          Files/issue2/evidence/*.json      (audit file, read back externally)
```

### Why one Lakehouse rather than three

The reference medallion gives each layer its own Lakehouse or workspace. That is
not available here: workspace creation is not authorised, and the only isolation
is a folder, which **is not a boundary** — Lakehouse tables do not live in
folders at all (`docs/environment-and-constraints.md`).

Layer separation is therefore carried by **table-name prefix** (`issue2_bronze_`,
`issue2_silver_`, `issue2_gold_`) inside one ticket-owned Lakehouse. That is
weaker than physical separation and is stated as such rather than described as a
sandbox. What it does buy is that every write this ticket performs lands inside
one item the ticket created, so reversal is the deletion of that item.

### Fabric items created

| Item | Type | Role |
|---|---|---|
| `issue2_retail_lakehouse` | Lakehouse | All tables and files |
| `issue2_00_generate_source` | Notebook | Deterministic synthetic source |
| `issue2_10_bronze_ingest` | Notebook | CSV → Bronze Delta |
| `issue2_20_silver_transform` | Notebook | Type, validate, quarantine, deduplicate |
| `issue2_30_gold_build` | Notebook | Three Gold aggregates |
| `issue2_90_validate` | Notebook | Reconcile everything, write the audit file |
| `issue2_retail_medallion_pipeline` | DataPipeline | Sequential orchestration, concurrency 1 |

**Auto-generated companions.** Creating a Lakehouse causes Fabric to create a SQL
analytics endpoint and a default semantic model, both sharing the Lakehouse's
display name. This ticket does not author them and does not claim to create
them, but they *will* appear in the post-deployment inventory diff. They are
declared in `config/issue2-allowlist.json` under
`expectedAutoGeneratedCompanions` so the diff can tell a documented platform side
effect from an undeclared change.

This is also why the inventory diff keys on **name *and* type**. On name alone
those three items collapse into one entry and two real items become invisible.

## 3. Synthetic source data

Generated by `issue2_00_generate_source`, parameterised entirely by
`src/issue2-retail-medallion/data-contract.json`.

| Parameter | Value | Derived expectation |
|---|---|---|
| Days | 90 | Gold daily grain = 90 × 8 = **720** |
| Stores | 8 | |
| Products | 40 | Gold product grain = **40** |
| Customers | 300 | |
| Segments | 4 | Gold segment grain = **4** |
| Lines per store-day | 7 | Clean lines = 90 × 8 × 7 = **5 040** |

### There is no random number generator

Every value is integer arithmetic over the row index. A re-run regenerates
byte-identical source data.

This matters for one specific reason: it is what makes the idempotency assertion
meaningful. If the generator were random, a stable row count across two runs
would prove only that the *count* was stable — not that the pipeline was
idempotent. With a deterministic generator, the Gold **content hashes** must be
identical, which is a far stronger claim.

Prices are held in integer cents and converted once, so the generator carries no
binary floating-point error into the source. Any rounding difference observed
downstream is attributable to the transformation under test.

### Injected defects

| Defect | Rows | Becomes |
|---|---|---|
| Non-positive quantity | 25 | `non_positive_quantity` |
| Null product id | 15 | `null_natural_key` |
| Orphan store id (999) | 20 | `orphan_store` |
| Non-positive price | 10 | `non_positive_price` |
| **Duplicate lines** | **60** | **deduplicated, not quarantined** |
| Total injected | 130 | |

Each defect row starts from a clean template and mutates **exactly one field**,
so no row can be rejected for two reasons. That is what makes the expected
per-reason breakdown exact rather than approximate: no reason can absorb
another's count and hide a rule that never fired.

Defect rows use a separate transaction-id namespace (`TXD-`) so a defect is never
also a duplicate. **Rejection and duplication are different failures with
different fixes** — a rejected row is bad data, a duplicated row is good data
delivered twice — and the design keeps them separable throughout.

Total source: 5 040 + 130 = **5 170** sales lines.

## 4. Data-quality rules

Declared in the contract, applied in `issue2_20_silver_transform`,
**first match wins**.

| # | Rule | Severity | Expected |
|---|---|---|---|
| 1 | `null_natural_key` — transaction_id, line_number or product_id null | reject | 15 |
| 2 | `non_positive_quantity` — quantity null or ≤ 0 | reject | 25 |
| 3 | `non_positive_price` — unit_price null or ≤ 0 | reject | 10 |
| 4 | `orphan_store` — no matching store dimension row | reject | 20 |
| 5 | `orphan_product` — no matching product dimension row | reject | **0** |
| 6 | `invalid_discount` — null, negative or > 0.9 | reject | **0** |
| 7 | `duplicate_line` — repeated (transaction_id, line_number) | dedupe | 60 |

### Precedence is not incidental

Rules are evaluated in the order above and a row carries exactly one reason.
Without a fixed precedence, a row with a null `product_id` would satisfy both
rule 1 and rule 5, the two counts would overlap, and the exact expected breakdown
would be unassertable.

### Zero is a real assertion

Rules 5 and 6 are expected to match nothing, and are asserted as `0` rather than
omitted. `0` says *the rule ran and found nothing*. An absent key would leave a
rule that never executes indistinguishable from one that executed cleanly.

### Rejected rows are never dropped

They go to `issue2_silver_quarantine_sales` with the reason attached. A rejected
row that vanished would be indistinguishable from a row that was never sent.

### Casting is non-destructive

An unparseable value becomes NULL and is then rejected by a named rule, rather
than throwing. One bad row should quarantine one row, not fail a pipeline.

### Deduplication is deterministic

The survivor is the lowest `source_row_id`, so the original survives and the copy
is dropped. Spark offers no stable "first row" without an explicit ordering, so
"keep one" would otherwise select a different row each run and the layer would
stop being reproducible even though its row count looked stable.

Deduplication runs **only over rows that already passed the quality rules**, so a
duplicated bad row is quarantined once rather than deduplicated into invisibility.

### Money is decimal, never double

`decimal(18,2)` throughout. A retail margin computed in binary floating point
drifts, and the financial reconciliation would then be measuring the arithmetic
rather than the transformation.

## 5. Gold layer

| Table | Grain | Rows | Question answered |
|---|---|---|---|
| `issue2_gold_daily_store_sales` | date × store | 720 | How is each store trading day to day? |
| `issue2_gold_product_performance` | product | 40 | Which products earn their shelf space? |
| `issue2_gold_customer_segment_kpi` | segment | 4 | What is each segment worth per head? |

Design decisions worth naming:

- **`transaction_count` counts distinct transactions, not lines.** A basket of
  seven items is one visit; counting lines would overstate footfall by the
  average basket size.
- **`active_customers` counts customers that transacted**, not the size of the
  segment in the dimension. Revenue per *registered* and per *active* customer
  are different numbers, and reporting the first under the second's name is the
  standard way this KPI goes wrong.
- **Margin uses the dimension's `unit_cost`**, not a cost carried on the fact, so
  a cost correction lands in one place.
- **`margin_pct` guards a zero denominator** explicitly. It cannot occur with
  this data, but a divide-by-zero that "cannot happen" is the cheapest possible
  thing to rule out.

All three aggregate the **same** `issue2_silver_sales.net_amount` column at three
independent grains, which is what makes the three-way agreement below a real
check on grouping rather than three re-derivations of one formula.

## 6. Validation approach

Twelve assertions, all in `issue2_90_validate`, every expected value read from
the contract committed **before** the run.

| # | Assertion | Catches |
|---|---|---|
| 1 | Landing row counts | Generator drift |
| 2 | Bronze row counts | Silent filtering in ingest |
| 3 | Silver row counts | Over- or under-rejection |
| 4 | Gold row counts | Wrong grain |
| 5 | Quarantine breakdown by reason | A rule that never fires |
| 6 | Row conservation | A silently dropped row |
| 7 | Duplicates removed | Dedup that removed too much or nothing |
| 8 | Primary-key uniqueness | Join fan-out |
| 9 | NULLs in key columns | A key that is not a key |
| 10 | Three-way financial agreement | Grouping and fan-out errors |
| 11 | Gold content hashes | Non-deterministic output |
| 12 | Idempotency vs previous run | A pipeline that is not re-runnable |

### Row conservation

```
bronze_sales = silver_sales + quarantined + deduplicated
5 170        = 5 040        + 70          + 60
```

Every source row is accounted for exactly once. The three terms come from three
independently written tables, so a bug would have to shift all three in the same
direction to hide. `duplicates_removed` is **derived** from this identity rather
than read from a counter the transform emitted — reading the transform's own
counter back would only confirm the transform agreed with itself.

### Financial reconciliation

`net_amount = quantity × unit_price × (1 − discount_pct)`, summed four ways: the
Silver fact plus all three Gold grains. Tolerance is **0.01 absolute**; cent-scale
rounding over ~5 000 rows is the only legitimate source of difference.

The customer-segment grain is the one that can legitimately disagree — it is the
only Gold table built through a join — which is exactly why it is included rather
than assumed equivalent.

### Idempotency

The pipeline runs **twice** in one deployment. Content hashes of the Gold tables
must be identical between runs. Lineage columns (leading underscore: `run_token`,
ingestion timestamps) are excluded, since they are *expected* to differ and
including them would guarantee a mismatch and make the check assert nothing.

Idempotency comes from every write being `mode("overwrite")` of a ticket-owned
path from deterministic source data. There is no append and no in-place mutation.

The check runs **twice, independently**: once inside stage 90 against the previous
run's audit file, and once in the deployment script across the two audit files it
retrieved itself. Neither is trusted to stand alone.

### How a row count is read back — open decision 1, resolved

`docs/environment-and-constraints.md` recorded this as the highest-priority open
decision. The resolution implemented here:

Stage 90 writes a machine-readable audit file to
`Files/issue2/evidence/validation-run-<token>.json`. The deployment script then
retrieves it over the **OneLake DFS endpoint** using the `storage.azure.com`
token audience — a different endpoint and a different token from the ones that
wrote it.

That indirection is the point. Evidence retrieved through the same component that
produced it only demonstrates that the component is self-consistent. No ODBC
driver and no semantic model are required.

The audit file is written **before** any failure is raised and carries an explicit
`passed` flag, so a failed run still leaves retrievable evidence naming the
assertion that failed. An audit file that existed only on success would make
every failure look like an infrastructure problem.

### Failing loudly

Stage 90 raises on any failed assertion. That is what makes a red validation
surface as a **failed pipeline run** rather than a `Succeeded` one that printed
some warnings. `Deploy-Issue2Medallion.ps1` polls to a terminal state and exits
non-zero on anything that is not `Succeeded`; a timeout reports `TimedOut`, never
success.

## 7. Offline tests

`tests/issue2-validation.tests.ps1` — **62 assertions, no Fabric access, no
authentication, no state change.** Runnable by a reviewer from a cold checkout.

| Group | Covers |
|---|---|
| Contract arithmetic | Every expected value recomputed from the generation parameters |
| Definitions and allowlist | Prefixes, `.platform` agreement, both directions of src ↔ allowlist |
| Pipeline wiring | Strict `Succeeded` chain, concurrency 1, no retries, all parameters bound |
| Data-path allowlist | Containment, prefixes, full coverage of contract tables |
| **Safety functions reject** | Deliberately bad input to every guard |
| Identifier hygiene | No GUID or email in any tracked Issue #2 file |
| Script hygiene | Parse, `Plan` default, no secret parameters |

The fifth group is the one that matters most. **A guard that has only ever been
shown to pass is not a guard.** Those tests feed undeclared items, unprefixed
names, out-of-scope data paths, mutated audit files and a widened tolerance to
each safety function and assert that it refuses.

## 9. Assumptions

1. **Fabric REST item creation accepts `folderId` on the create call.** Used to
   place every item in the authorised folder. `Publish-FabricItemDefinition`
   verifies the landing folder on read-back and fails if it differs, so a wrong
   assumption surfaces as a failure rather than as a misplaced item.
2. **`notebookutils.fs.put` / `.head` are available in the Fabric Spark runtime.**
   Used for the audit file. A fallback to `mssparkutils` is in place.
3. **The Items API reports `folderId` reliably**, per open decision 2, already
   recorded as resolved.
4. **`decimal(18,2)` is sufficient** for all monetary values at this data volume.
5. **The TridentNotebook activity and pipeline definition shape** match the
   current Fabric pipeline schema. **Unverified against a live tenant** — see
   limitations.

## 10. Limitations

- **No runtime evidence exists.** No pipeline has run. Every claim about row
  counts, reconciliation and idempotency is a claim about what the code *will*
  produce, derived from contract arithmetic and offline tests — not an
  observation. The evidence package records this explicitly rather than
  presenting expected values as observed ones.
- **The pipeline and notebook definition shapes are unvalidated against Fabric.**
  They follow the documented schema, but no deployment has confirmed the API
  accepts them. This is the most likely source of first-run failure.
- **In-place modification of an existing item is undetectable.** The Items API
  returns no definition hash, so `definitionHash` records the literal string
  `not-captured` and the inventory diff detects additions and removals only.
  This is open decision 6 and is not closed by this ticket.
- **Layer isolation is by table-name prefix**, not by separate storage. Weaker
  than the reference pattern; see §2.
- **The folder is not a security boundary**, and nothing at the identity layer
  prevents a rule violation. Every Fabric restriction here is an instruction.
- **A shared, modest capacity.** The pipeline is sequential with concurrency 1
  and no retries, but a Spark run can still throttle other users' work.

## 11. Reversal and cleanup

Generated before any write by `New-ReversalPlan` into
[`reviews/2/reversal-plan.md`](../reviews/2/reversal-plan.md).

Order: pipeline → notebooks → Lakehouse **last**. The Lakehouse holds every table
and file, so deleting it first would strand the other items and discard the
evidence files before they could be retrieved.

**No agent executes any reversal step.** Cleanup is human (CLAUDE.md rule 5).

**Data-loss risk: none.** All data is synthetic, deterministic and regenerable
from `data-contract.json` by re-running the pipeline.

Repository reversal: close the pull request without merging and delete the
feature branch.

## 12. Evidence handling

| Artefact | Location | Committed |
|---|---|---|
| Raw run output, real GUIDs | `runtime/issue2/` | **No** — gitignored |
| Sanitized evidence | `reviews/2/evidence.json` | Yes |
| Reversal plan | `reviews/2/reversal-plan.md` | Yes |

`Write-Issue2Evidence.ps1` redacts rather than omits: a GUID becomes a stable
placeholder such as `<workspace>` or `<item:issue2_retail_lakehouse>`, so a
reviewer can still follow which item a claim refers to. Deleting the field
instead would make the package unreviewable exactly where it matters.

The actual control is that the script **refuses to write an output file
containing anything GUID-shaped**, including GUIDs its named redaction map did
not anticipate — an unrecognised identifier in the output is more dangerous than
a recognised one, not less.
